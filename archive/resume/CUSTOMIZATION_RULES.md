# 이력서 커스터마이징 규칙

이 문서는 회사와 직무별로 이력서를 수정할 때 사용하는 체크리스트다. `index.html`을 원본으로 관리하고, 수정 후 PDF를 다시 생성한다.

## 1. 포지션 타이틀을 지원 직무에 맞춘다

`FRONTEND-FOCUSED FULL-STACK SOFTWARE ENGINEER`처럼 범위가 넓고 긴 기본 타이틀을 그대로 사용하지 않는다. 채용 공고가 가장 먼저 찾는 역할 하나를 구체적으로 제시한다.

예시:

- 프론트엔드 직무: `FRONTEND ENGINEER`
- React 중심 직무: `REACT FRONTEND ENGINEER`
- 공간정보 플랫폼 직무: `3D·GIS FRONTEND ENGINEER`
- 풀스택 직무: `FULL-STACK SOFTWARE ENGINEER`
- 인프라 비중이 큰 직무: `SOFTWARE ENGINEER · PLATFORM & INFRASTRUCTURE`

타이틀과 SUMMARY 첫 문장은 반드시 같은 직무 정체성을 가리켜야 한다.

## 2. 기술 스택은 지원 직무에 맞춰 재정렬한다

현재의 `Frontend / Backend / 3D·Spatial / Infra·DevOps / Architecture` 그룹 구조는 유지한다. 다만 모든 지원서에서 같은 순서와 내용을 고정하지 않는다.

- 공고의 필수·우대 기술과 직접 연결되는 그룹을 가장 위에 둔다.
- 각 그룹 안에서도 공고와 연관성이 높은 기술부터 배치한다.
- 공고와 무관하거나 설명할 경험이 약한 기술은 제거한다.
- 기술이 과도하게 나열되면 전체 핵심 스택을 12~15개 수준으로 압축한다.
- 나열한 기술은 반드시 CAREER 또는 WORK 항목에서 사용 맥락을 확인할 수 있어야 한다.

## 3. 경력은 Problem → Solution → Result로 쓴다

기능 목록만 나열하지 않는다. 각 문장은 가능하면 아래 세 요소를 한 흐름으로 담는다.

1. **Problem:** 어떤 제약, 병목, 운영 문제 또는 사용자 문제가 있었는가?
2. **Solution:** 어떤 기술적 판단을 내리고 무엇을 설계·구현했는가?
3. **Result:** 성능, 안정성, 비용, 생산성 또는 사용자 경험이 어떻게 달라졌는가?

기본 문장 틀:

> `[문제/제약]`이 발생하자 `[기술적 선택과 구현]`으로 해결해 `[검증 가능한 결과]`를 만들었다.

결과는 수치가 있으면 수치로 쓰고, 수치가 없으면 운영 안정화·자동화·인증 취득·업무 통합처럼 확인 가능한 변화로 쓴다. 근거 없는 성능 향상이나 비용 절감 수치는 만들지 않는다.

## 4. 공고별 최종 점검

- 타이틀이 채용 공고의 직무명과 바로 연결되는가?
- SUMMARY 첫 두 문장에 해당 직무의 핵심 역량과 대표 성과가 드러나는가?
- 가장 관련성 높은 프로젝트가 `SELECTED WORK` 상단에 있는가?
- 공고의 핵심 키워드가 기술 스택뿐 아니라 경력 문장에도 자연스럽게 등장하는가?
- 각 주요 경력에서 문제, 해결 방법, 결과를 읽을 수 있는가?
- 삭제하거나 축약한 내용 때문에 프로젝트의 맥락이 끊기지 않았는가?
- HTML 수정 후 PDF를 다시 생성하고 페이지 잘림과 링크를 확인했는가?
